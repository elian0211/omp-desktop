# In-app updates

`src-tauri/src/updater.rs` over `tauri-plugin-updater` (issue #19). The feed is `latest.json` on the newest **published, non-prerelease** GitHub release (`plugins.updater.endpoints` in `tauri.conf.json`), verified against the minisign key in `plugins.updater.pubkey`. Two commands: `app_update_check` parks the plugin's `Update` in `UpdaterState` and returns a serialisable `UpdateInfo`, and `app_update_install` installs whatever is parked. The download URL never crosses IPC, so the webview can only install what the signed feed announced. Progress arrives as throttled `update://progress` events.

- **Self-install is deliberately narrower than the plugin** (`can_self_install`): only AppImage/MSI/NSIS/`.app`. On macOS the executable must also sit in `*.app/Contents/MacOS`. tauri-utils reports `BundleType::App` for *every* unpatched macOS binary, and for a `tauri dev` binary the plugin would move `target/debug` away and delete it. `.deb`/`.rpm` (the plugin would `pkexec dpkg -i`, falling back to a TTY `sudo`) and unbundled `tauri dev`/source builds are notify-only; the UI links to the release page instead.
- **Relaunch skips `Drop`.** Off Windows, `request_restart` ends the process without dropping managed state, so `AgentBridge::shutdown_all` kills the omp children explicitly first; on Unix they sit in their own process group and would be orphaned otherwise. On Windows the plugin exits right after launching the installer, and the `KILL_ON_JOB_CLOSE` job objects take every omp tree down with the process. We deliberately don't override the plugin's `on_before_exit`: it runs *before* the installer launch, and killing omp there would strand every tab if the launch then failed.
- **The MSI relaunch has a cut-down PATH.** After an MSI update the new version is started by the installer's `LaunchApplication` custom action inside the Windows Installer service: profile vars (`LOCALAPPDATA`, `USERPROFILE`, user-defined ones) are right, but PATH is the machine PATH only — no user PATH, so a per-user omp (`%LOCALAPPDATA%\omp`) isn't found (#34). `src-tauri/src/child_path.rs` (`child_path`: inherited PATH first, then the Unix GUI-launcher install dirs / on Windows the registry's machine + user PATH) is what every omp run (`spawn::Omp`) and every `git` spawn (`workspace::git`) search, both through `child_path_dirs` + `locate_program`; any new child that must resolve a user-installed binary needs the same.
- Frontend: `app/updater.js` is the pure reducer plus the shared phase selectors `isBusy`/`isInstalling` (regression: `test-updater.mjs`). `app/use-updater.jsx` owns the timer (15 s after launch, then every 6 h) and the modal state; its public `check()` is always a manual check. Download progress is subscribed only for the duration of `OMP_BRIDGE.installUpdate(onProgress)`. `design/update-modal.jsx` renders it. A background check never opens anything; it only lights the status-bar version button. The `updateCheck`/`skippedUpdate` tweaks persist auto-check and "skip this version"; Settings → Session shows both (the `version` row, `design/settings/rows-session.jsx`: version, last check, "Check now", the skipped release with "Clear skipped" = `clearSkipped`, which sets `skippedUpdate` to `null` so the version button offers it again). Release notes render as plain text: `notes` is not covered by the signature.
- Release signing: `bundle.createUpdaterArtifacts` lives in `src-tauri/tauri.release.conf.json`, merged only by `release.yml` (`--config`); in `tauri.conf.json` it would make every local `npm run build` fail for lack of the private key. The key lives only in the `TAURI_SIGNING_PRIVATE_KEY` repo secret (plus `_PASSWORD` if it has one) and is **never** committed. Rotating it strands every installed copy.
- Release notes have one source, the version's `## [X.Y.Z]` section of `CHANGELOG.md`: `.github/scripts/updater-json.mjs` puts it in the feed's `notes` (the update modal), and `.github/scripts/release-notes.mjs` writes it, followed by the installation text, as the GitHub release page's body (`release.yml`'s `updater-json` job, `gh release edit --notes-file`; tauri-action creates the draft without a body). A stable tag without that section fails the job before the feed is uploaded; a prerelease falls back to `## [Unreleased]`.

## omp version and update check

omp owns its own updater (`omp update` / `omp update --check`). The desktop never installs omp: it only surfaces what that CLI prints.

- **Setup guide** (`app/omp-setup.js`, `app/use-omp-setup.jsx`, `design/omp-setup-modal.jsx`; regression `test-omp-setup.mjs`): one `omp_locate` boot check (`lib.rs` → `spawn::omp_binary_path`, a few filesystem lookups, no child run). No omp on the trusted PATH → the modal shows the official install one-liner per OS and the npm command (copy buttons) and opens omp.sh through `open_url_external` on request. "Check again" re-invokes `omp_locate`: the resolve is per call, so an install needs no app restart.

- **Rust** (`src-tauri/src/omp_update.rs`): `omp_version` runs `omp --version` (via `spawn::omp_output_plain`, colour forced off); `omp_update_check` runs `omp update --check` and parses the human stdout (ANSI stripped) into `OmpUpdateInfo` (`version`, `available`, `canUpdate`, `reason`). There is no machine-readable flag yet — the parser matches omp's known phrases (`Current version:`, `New version available:`, `Already up to date`, Nix/managed-app refusals). Channels, package rename and binary-only releases stay omp's problem; the desktop does not query npm itself.
- **Frontend**: `app/omp-updater.js` (pure reducer; regression `test-omp-updater.mjs`), `app/use-omp-updater.jsx` (timer staggered 20 s after launch, then every 6 h, sharing the desktop's `updateCheck` tweak; `skippedOmpUpdate` for skip), `design/omp-update-modal.jsx` (copy `omp update`, no install). The status bar shows `desktop v…` and `omp v…`; an available update lights its button up (accent + dot, hover rolls the label to the new version, click opens the modal) instead of a pill of its own (`design/chrome.jsx` `VersionButton`); Settings → Session → Version shows both (`design/settings/rows-session.jsx`).
